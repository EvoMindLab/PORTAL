# PORTAL Type 3 Dataset Runner

This workflow mass-produces concrete PORTAL instances from a selected suite or
another user-declared source bank. It applies only the Type 3 (`augment`)
realization mechanism and writes canonical unified JSON files.

It deliberately does **not** calculate ELA or Performance features, run optimizers,
deduplicate recipes, or select another suite. The source bank defines the
structural scope of the generated dataset. Type 3 then supplies controlled
large-scale variation within that declared scope.

For each concrete instance, Type 3 resamples component centers and basin
depths under the declared bounds, applies the controlled parameter shuffles
defined by the realization mechanism, recomputes dependent calibration
terms, and, for multi-block recipes, reassigns the existing block weights. The
block-local no-cover safeguard rejects and redraws center/depth proposals that
would hide a component center, unless the user explicitly disables it.

## Quick start

Copy the example configuration, choose a source bank and output directory, and
set the number of instances required from each source recipe:

```powershell
Copy-Item augmentation_dataset.example.toml augmentation_dataset.toml
python run_augmentation_dataset.py --config augmentation_dataset.toml --dry-run
python run_augmentation_dataset.py --config augmentation_dataset.toml
```

The dry run validates every source as a canonical unified PORTAL JSON,
validates its metadata and search bounds, and prints the resolved workload. It
does not create an output directory.

## Source bank

`run.sources` accepts one or more JSON files or directories. Directories are
searched recursively. Recipe identity and family membership are read from the
JSON metadata, not inferred from directory names, so a flat folder is valid.

Source recipe identifiers and source contents must be unique. The runner also
rejects identifiers that would collapse to the same portable output path under
the selected layout. An output directory cannot be placed inside a source
directory, because generated JSONs must never become inputs to a resumed run.

The runner accepts mixed recipe dimensions. The configured scalar center range
must fit inside every source recipe's search bounds.

## Type 3 controls

The `[generation]` table exposes all Type 3 controls used by
`portal_core.realization.realize`:

| Key | Meaning |
|---|---|
| `count_per_recipe` | Number of generated instances per source recipe. |
| `start_sample` | First deterministic sample identifier. |
| `base_seed` | Dataset-level base seed. |
| `center_min`, `center_max` | Uniform center-resampling range on each block-local dimension. |
| `beta_min`, `beta_max` | Permitted basin-depth range. |
| `beta_gap` | Maximum depth span within one block. |
| `beta_opt_gap` | Minimum gap from the selected block optimum to nonoptimal basins. |
| `ensure_no_cover` | Require every component center to remain exposed in its own Layer-2 block. |
| `no_cover_max_attempts` | Maximum proposal rounds before a task fails. |
| `no_cover_tolerance` | Numerical tolerance for the block-local exposure check. |
| `trace_metadata` | Include additional block trace metadata in each JSON. |

For each source recipe, the Type 3 random stream is keyed by its content
fingerprint together with `base_seed` and `sample_id`. The same source bytes and
generation settings therefore reproduce the same concrete instances. Changing
the source recipe content changes its augmentation stream.

Released JSON files are versioned without Git line-ending conversion so their
source-byte fingerprints remain stable across checkouts. Reformatting a source
file changes that fingerprint even if its numerical parameters are unchanged.

## Parallel execution and progress

The runner uses worker processes. With `max_workers = 0`, it uses
`floor(cpu_count * cpu_fraction)`, with at least one worker. The example uses
95% of available logical CPU cores. Set an explicit positive `max_workers` to
override the fraction. Worker counts are capped by the available CPU count,
pending work, and Windows' limit of 61 process-executor workers.

`task_chunk_size` controls how many sample IDs from one recipe are generated by
one submitted worker task. `max_in_flight_factor` bounds queued work, so very
large datasets do not require every task to be held by the process executor at
once. Worker processes are restricted to one BLAS/OpenMP thread to avoid nested
CPU oversubscription.

The console and `logs/augmentation.log` report:

- resolved source, family, dimension, and output counts;
- worker, chunk, and in-flight settings;
- completed instances and percentage;
- elapsed time, throughput, and estimated remaining time;
- quiet-time alive messages during slow chunks;
- resume audits and any failed recipe/sample identifier.

## Atomic output and resume

Each JSON is first written to a temporary file in its destination directory and
then atomically moved to its final name. The parent process is the only writer
of the append-only task checkpoint.

With `run.resume = true`, rerunning the same command audits the checkpoint and
reuses only tasks whose source hash, generation signature, output file, and,
when enabled, output hash remain compatible. Missing, stale, or corrupt outputs
are regenerated. Worker-count, chunk-size, heartbeat, and checkpoint-frequency
settings may be changed without changing generated-instance identity.

The runner refuses to mix outputs from different source banks, generation
contracts, implementation versions, or Python/NumPy numerical environments.
Use a new `output_root`, or pass `--force` to replace only a prior directory
that contains the runner's state marker. `--force` never deletes a non-empty
unmarked directory.

## Output layout

The default layout is:

```text
OUTPUT_ROOT/
+-- instances/
|   +-- Family1/
|       +-- f01_r001/
|           +-- f01_r001__type3_s000001.json
+-- logs/
|   +-- augmentation.log
+-- metadata/
    +-- completed_tasks.jsonl
    +-- config.resolved.json
    +-- instance_manifest.csv
    +-- run_manifest.json
    +-- run_state.json
    +-- source_manifest.csv
    +-- summary.json
    +-- summary.md
```

`output.layout` may instead be `by_recipe` or `flat`. Output filenames include
the source recipe identifier and deterministic sample identifier. The source
recipe hash, generation signature, verification result, no-cover rejection
count, and output hash are retained in the manifest.

## Validation

Saving always passes through the canonical unified-schema serializer. With
`validation.verify_outputs = true`, every output is then reloaded and checked
for:

- the declared Type 3 realization method;
- finite center and basin-depth values, requested ranges, and depth gaps;
- preservation of block counts, local dimensions, and the block-weight multiset;
- known-optimum consistency under block weights;
- block-local component exposure when the safeguard is enabled.

This validation adds runtime but is recommended for released datasets.

## Relationship to the simple utility

`Recipe_Selection/run_augmentation.py` remains available for small, direct,
sequential jobs. The root-level `run_augmentation_dataset.py` is the preferred
entry point for long or publishable dataset runs because it adds strict
configuration, parallel execution, atomic writes, provenance, progress logs,
and resumable state.
